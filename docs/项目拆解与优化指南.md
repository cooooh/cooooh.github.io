## 一、全景：一个网页是怎么到你眼前的

Snowtrace 是**静态博客**：网站上所有的页面，都是你本地电脑「预先算好」的一堆文件。
访客打开网站时，服务器只是把这些文件原样发过去，没有任何程序在服务器上运行。

完整流水线：

```text
① 写内容                 source/_posts/*.md、source/xxx/index.md（Markdown 文本）
        ↓
② 构建（npx hexo generate）
        把「内容 + 主题模板 + 配置」混合，生成最终网页
        ↓
③ 产物                 public/ 目录（纯 HTML/CSS/JS/图片，就是网站本身）
        ↓
④ 上传（git push）      提交到 GitHub 仓库的 main 分支
        ↓
⑤ 自动部署（GitHub Actions）
        .github/workflows/deploy.yml 在 GitHub 的服务器上重新跑一遍构建
        把 public/ 推到 gh-pages 分支
        ↓
⑥ 托管（GitHub Pages）    GitHub 把 gh-pages 分支当网站发出去
        ↓
⑦ 域名                 snowtrace.top 的 DNS 记录指向 GitHub 的服务器
        ↓
⑧ 访客浏览器           拿到 HTML → 再下载 CSS/JS/图片 → 渲染出你看到的页面
```

几个关键角色：

| 角色 | 是什么 | 在项目里的位置 |
|------|--------|--------------|
| 站点配置 | 网站叫什么、网址、语言等 | `_config.yml` |
| 主题配置 | 长什么样、有哪些功能开关 | `_config.butterfly.yml` |
| 主题 | 一套「长相模板」，把内容套进去 | `node_modules/hexo-theme-butterfly/` |
| 内容 | 你的文章和页面 | `source/` |
| 自定义脚本/样式 | 主题没提供、我们自己加的功能 | `source/js/`、`source/css/` |
| 构建工具 | 把上面几样搅在一起产出网页 | Hexo（`npm` 安装的命令行工具） |
| 部署管道 | 推送后自动构建+发布的机器人 | `.github/workflows/deploy.yml` |

**最重要的一句话**：网站上一切能看到的页面，都不是「实时生成」的，
而是从 `source/` 里的文字 + 配置 + 模板**提前算出来的**。
所以改完东西要重新构建（本地 `npx hexo generate`，线上由 Actions 自动做），访客才能看到新版本。

## 二、目录结构逐个讲

```text
Snowtrace/
├── _config.yml               # ① 站点配置（标题、网址、语言、文章格式…）
├── _config.butterfly.yml     # ② 主题配置（导航、头像、开关、注入…）
├── package.json              # ③ 项目清单：装了哪些依赖、有哪些快捷命令
├── package-lock.json         # 依赖的精确版本锁定文件（自动生成，不要手改）
├── node_modules/             # ④ 装好的依赖（Hexo、主题、插件都在里面，不要动）
├── .gitignore                # ⑤ 告诉 git 哪些文件/目录不提交
├── README.md                 # ⑥ 项目说明文档
├── docs/                     # ⑦ 学习文档（本文件在这）
├── scaffolds/                # ⑧ 新文章模板（hexo new 时按它生成）
├── source/                   # ⑨ 内容根目录——你 90% 的写作都发生在这
│   ├── _posts/               #    文章（Markdown）
│   ├── about/index.md        #    关于页
│   ├── log/index.md          #    更新日志页
│   ├── music/index.md        #    音乐页
│   ├── link/index.md         #    友链页
│   ├── categories/index.md   #    分类页
│   ├── tags/index.md         #    标签页
│   ├── _data/link.yml        #    友链数据（页面和数据分离）
│   ├── img/                  #    图片（头像、图标、封面…）
│   ├── js/                   #    自定义脚本（我们写的功能逻辑）
│   ├── css/                  #    自定义样式（我们写的外观）
│   └── CNAME                 #    自定义域名声明
├── public/                   # ⑩ 构建产物（自动生成，永远不要手改）
└── .github/workflows/deploy.yml  # ⑪ 自动部署脚本
```

### ① `_config.yml` —— 站点级配置

Hexo 启动时第一份读的配置。你现在最该认识这些字段：

| 字段（位置） | 作用 |
|-------------|------|
| `title` / `subtitle` / `author`（约第 5~9 行） | 网站名、副标题、作者名 |
| `language`（第 10 行） | 界面语言（zh-CN） |
| `url`（第 14 行） | 网站正式地址。**它影响所有绝对链接的生成**，所以绑定域名后必须改它 |
| `permalink`（第 16 行） | 文章网址的格式 |
| `post_asset_folder`（第 42 行） | 为每篇文章建同名资源文件夹 |
| `default_category`（第 66 行） | 文章不写分类时的默认分类 |
| `search`（第 97~101 行） | 本地搜索索引的生成参数 |

### ② `_config.butterfly.yml` —— 主题配置

这是全项目**最常改的文件**。它是 Butterfly 主题全部设置的清单，
字段名字都能在主题文档查到。本项目用过的重点：

| 段落 | 我们用它做了什么 |
|------|----------------|
| `menu`（第 20~29 行） | 导航栏；注意「关于」是**嵌套写法**（缩进的子项=下拉菜单） |
| `avatar.img`（第 63~65 行） | 侧边栏头像 |
| `subtitle`（第 156~173 行） | 首页那句诗 |
| `footer.custom_text`（第 264~273 行） | 页脚文字 |
| `card_announcement.content`（第 299~302 行） | 侧边栏公告 |
| `search`（第 480~499 行） | 搜索功能开关 |
| `aplayerInject`（第 999~1001 行） | 音乐播放器资源开关 |
| `inject`（第 1065~1080 行） | **把自定义 CSS/JS 插进网页**（见第三节） |
| `CDN`（第 1079~1088 行） | 静态资源走本地还是 CDN |

### ⑨ `source/` —— 内容根目录

规则很简单：**这里的每个文件夹都会变成网站上的一个网址**。

- `source/_posts/xxx.md` → 一篇文章
- `source/about/index.md` → `/about/` 页面
- `source/img/avatar.svg` → `/img/avatar.svg` 图片
- `source/js/music-page.js` → `/js/music-page.js` 脚本文件
- 下划线开头的（`_posts`、`_data`）是**特殊目录**，会被 Hexo 特殊处理，不会原样出现在网址里

每个 `.md` 文件开头由 `---` 包起来的部分叫 **front-matter**（见第三节）。

### ⑩ `public/` —— 构建产物

`npx hexo generate` 之后生成。它是网站的「成品」，
本地预览和线上部署用的都是它。**永远不要手动编辑**，它随时会被重新生成覆盖。

### ⑪ `.github/workflows/deploy.yml` —— 自动部署

一共四步（打开看，每步都有名字）：

1. `Checkout`：把仓库代码拉到 GitHub 的服务器
2. `Setup Node` + `Install dependencies`：装 Node 环境、装依赖
3. `Build`：跑 `npm run generate`，在你没注意的地方重新构建一遍
4. `Deploy to GitHub Pages`：把 `public/` 推送到 `gh-pages` 分支（含 CNAME 文件）

它在 `push` 到 main 分支时自动触发。也就是说：**你只管写好内容 push，构建不用自己做**。

## 三、核心机制逐个讲透

### 3.1 front-matter：每篇文章的「身份证」

每个 `.md` 文件顶部 `---` 之间的内容，是给 Hexo 看的元数据：

```text
title: 文章标题
date: 2026-08-21 10:00:00     ← 决定文章时间（影响归档、排序）
tags: [标签1, 标签2]          ← 决定标签页归类
categories: [知识]            ← 决定分类页归类
description: 一句话摘要        ← 首页卡片上的简介
```

页面（非文章）还会用：

```text
top_img: false      ← 该页要不要顶部大图
comments: false     ← 该页要不要评论区
aplayer: true       ← 音乐页独有：本页才加载播放器资源
```

### 3.2 主题模板：内容是怎么被「套」进去的

Butterfly 主题在 `node_modules/hexo-theme-butterfly/` 里，用 **Pug 模板**写页面骨架：

- `layout/includes/layout.pug` —— 整个页面的骨架（head、侧边栏、正文区、页脚）
- `layout/includes/header/index.pug` —— 顶部区域（首页大图、导航栏、站名副标题）
- `layout/includes/widget/card_author.pug` —— 侧边栏「作者卡片」（就是放头像的那个）

模板里读配置的方式是 `theme.xxx`（主题配置）和 `config.xxx`（站点配置）。
比如首页顶部那块：

- 配置里 `index_img` 有值 → 首页顶部出现全屏大图（class 叫 `full_page`）
- 没值 → 顶部没有大图区

**你现在不需要会写 Pug**，但要知道：主题功能都来自「配置 → 模板 → 网页」这条链。
想深挖某个功能，就去主题目录里搜对应配置字段名，看模板怎么用它。

### 3.3 inject 注入：不动主题也能加代码的「后门」

Butterfly 提供的官方机制。`_config.butterfly.yml` 第 1065~1080 行：

- `inject.head` 里的内容会被插进每个页面的 `</head>` 之前（放 CSS 链接）
- `inject.bottom` 里的内容会被插进每个页面的 `</body>` 之前（放 JS 脚本）

本项目靠它加载了 6 个自定义文件（3 个 CSS + 3 个 JS）。
**这是本站所有自定义功能的总入口**：新增任何自定义样式/脚本，第一步都是在这里登记一行。

### 3.4 localStorage：无后端网站怎么「记住」东西

静态站没有数据库。但浏览器自带一个「本地仓库」叫 localStorage：
每个网站可以在访客浏览器里存几 MB 的键值对数据，关了浏览器也在。

「个人设置」（换头像/首页背景）的原理：

1. 你选图 → JS 把图片压缩成文本（base64）→ 存进 localStorage（键名 `snowtrace.avatar` / `snowtrace.homeBg`）
2. 之后每次打开页面 → JS 启动时读这两个键 → 有值就替换头像/背景

代价：**数据跟着浏览器走**，换设备、换浏览器、清缓存就没了。
这就是它「只有自己看得见」的原因。想全局生效，唯一办法是把图片放进仓库（见 5.1）。

### 3.5 构建流程：hexo generate 到底干了什么

1. 读两份配置
2. 遍历 `source/` 下所有内容文件，解析 Markdown → 转成 HTML 片段
3. 根据主题模板，把每个 HTML 片段拼进页面骨架
4. 处理分类、标签、归档、搜索索引（`search.xml`）等聚合页
5. 把结果写进 `public/`
6. `source/` 里的静态文件（图片、js、css、CNAME）原样拷贝进 `public/`

本地预览（`npm run server`）背后是同一个流程，只是构建完顺手开了个本地网页服务器。
**注意**：改 `_config.butterfly.yml` 后预览服务器不会自动重建，必须重启；改 `source/` 里的文件则自动生效。

### 3.6 自定义域名：DNS 是什么

DNS 就像电话簿：把「snowtrace.top」翻译成服务器 IP。

- **A 记录**：名字 → IP（写死 GitHub 的 4 个 IP）
- **CNAME 记录**：名字 → 另一个名字（如 `www.snowtrace.top` → `cooooh.github.io`，IP 由 GitHub 自己管理，换 IP 不用你管）

GitHub 那边通过仓库里的 `source/CNAME` 文件 + Pages 设置认出这个域名，
然后自动签发 HTTPS 证书。整条链路：`域名 → DNS → GitHub Pages → public/ 里的文件`。

## 四、现有自定义代码导读

### 4.1 `source/js/music-page.js`（63 行）——音乐页脚本

结构分两段：

- **第 9~31 行「创建播放器」**：判断页面里有 `.music-stage` 才执行（防止其他页面白跑）；
  用 JS 动态创建一个 `meting-js` 标签，把歌单参数写在 `data-*` 属性里
  （`data-id` 是歌单 ID、`data-api` 是取歌单的后端接口模板、`data-theme` 是主题色）。
- **第 33~62 行「唱片联动」**：播放器是异步加载的，所以用 `setInterval` 每 250ms
  检查一次全局变量 `window.aplayers` 有没有就绪（最多 60 次）；就绪后绑定三个事件：
  `play`（加旋转类名）、`pause`（移除）、`listswitch`（换歌时把新封面贴到唱片上）。

学习点：`createElement` + `setAttribute` 动态建元素、轮询等待异步资源、事件回调里操作 class。

### 4.2 `source/js/changelog-modal.js`（87 行）——更新日志弹窗

- 第 14~37 行 `build()`：用 JS 拼出弹窗 HTML 挂到页面上，绑定关闭按钮、点背景关闭、按 Esc 关闭
- 第 43~63 行 `load()`：用 `fetch('/log/')` 把整个日志页抓下来，再用 `DOMParser`
  从中抠出正文部分（`#article-container`）塞进弹窗——**一个页面当两种用途用**
- 第 80~86 行：**事件委托**。不直接给菜单链接绑事件，而是在 `document` 上监听点击，
  凡是点中了 `a[href="/log/"]` 就拦截跳转、改弹窗。这样桌面导航和手机侧边栏的链接自动都生效

学习点：fetch 抓自己网站的页面、DOMParser 解析 HTML、事件委托、简单缓存（`cache` 变量）。

### 4.3 `source/js/site-settings.js`——个人设置

四个层次，是学「JS 操作页面」最完整的样板：

1. **应用层**（`applyAvatar` / `applyHomeBg`）：读 localStorage → 改页面（换 img 的 src、插入背景层 div）
2. **还原层**（`resetAvatar` / `resetHomeBg`）：删 localStorage 键 → 把页面改回去（靠 `dataset.origSrc` 记住原值）
3. **面板层**（`initPanel`）：关于页特有的表单逻辑——文件选择 → `loadFile` 压缩图片 → 预览 → 应用/还原按钮
4. **图片压缩**（`loadFile`）：`FileReader` 读文件 → `Image` + `canvas` 缩放重绘 → `toDataURL` 输出压缩版

学习点：localStorage 读写、canvas 图片处理、按钮事件、`dataset` 存临时数据、启动钩子 `DOMContentLoaded`。

### 4.4 CSS 文件们的套路

`source/css/music.css`（黑胶唱片 + 播放器卡片）：

- 第 43 行起 `.vinyl`：圆形唱片本体；第 90 行 `@keyframes vinyl-spin`：旋转动画定义；
  第 60 行 `.vinyl.playing`：播放时才启动动画 + 发光
- 第 101 行起 `#music-player .aplayer`：播放器卡片的「亚克力」效果——
  `backdrop-filter: blur(...)` 是毛玻璃关键属性
- 第 140 行 `.aplayer-list ol`：歌单区的内边距和分割线

`source/css/settings.css`（设置卡片 + 首页背景层）：

- 开头 `#snowtrace-home-bg`：JS 动态插入的固定背景层样式（`position: fixed; z-index: -1` 表示「垫在所有内容下面」）
- `[data-theme='dark']` 开头的选择器：暗色模式专用配色（跟着主题的 html 属性走）
- `.settings-btn` 一组：按钮三种形态（默认/primary 主色/ghost 幽灵），`input[type='file']` 用 `display:none` 藏起来、label 当按钮用

通用学习点：

- **CSS 变量**：主题提供的 `var(--font-color)`、`var(--card-bg)` 等，用它们才能自动适配暗色模式
- **选择器层级**：`#music-player .aplayer .aplayer-body` 这种长选择器是为了「只改这一处，不误伤全局」
- 改样式不需要重启预览，浏览器刷新即见

## 五、优化建议清单（按难度分级）

> 阅读方式：每项给出「现状 → 目标 → 动哪个文件哪一行 → 原理 → 注意」。
> 按你的要求，**只指路、不给改好的代码**。难度：★ 改配置/文案，★★ 改内容或加条目，
> ★★★ 需要读代码模仿，★★★★ 动部署或引入新服务。

### 5.1 给首页加一张默认背景图（★）

- **文件**：`_config.butterfly.yml` 第 98~101 行的 `background:` 字段
- **做法**：把图片放进 `source/img/`；把该字段的值从空改成图片地址（支持颜色、单图、多图数组——多图时每次刷新随机抽一张）
- **原理**：这个字段有值时，主题的 `layout.pug`（第 15~19 行）会在页面里生成 `<div id="web_bg">`，
  主题自带的 CSS（`node_modules/hexo-theme-butterfly/source/css/_global/index.styl` 第 137~146 行）已经写好了固定定位的样式
- **注意**：它和「个人设置」里的首页背景的关系——浏览器里设置的自定义背景层 z-index 更高，会盖住它；在设置面板点「恢复默认」后，露出来的就是这里配的图。两者不冲突，正好一「默认」一「个人」
- **改动后**：必须重启本地预览（主题配置不热更新），线上重新部署生效

### 5.2 换 favicon / 导航栏 logo（★）

- **文件**：`_config.butterfly.yml` 第 61 行 `favicon:` 和第 14 行 `nav.logo:`
- **做法**：新图放 `source/img/`，把字段值改成新路径；图标建议保持 SVG 或小尺寸 PNG

### 5.3 给文章加封面图（★）

- **文件**：目标文章的 `.md` 文件 front-matter
- **做法**：加一个 `cover:` 字段，值写图片路径（放文章资源文件夹或 `source/img/` 都行）
- **原理**：首页列表卡片、文章顶部大图都会用这个字段；不写时用主题的默认封面或纯色

### 5.4 维护友链（★）

- **文件**：`source/_data/link.yml`
- **做法**：文件里已经有注释掉的示例格式，按格式取消注释、逐条填写（名称/链接/头像/一句话）
- **原理**：这是「数据与页面分离」的写法——页面 `source/link/index.md` 负责长相，数据在 yml 里，加友链不用碰页面

### 5.5 改首页公告、页脚文字、关于页自我介绍（★）

- **文件**：
  - 公告：`_config.butterfly.yml` 第 299~302 行 `card_announcement.content`

### 5.7 换歌单 / 调播放器行为（★★）

### 5.9 给「个人设置」加新设置项（★★★，重点练习）

这是「读懂代码 → 模仿扩展」的最佳练手。以「自定义主题色」为例，完整链路：

1. **HTML**：`source/about/index.md` 里 `#site-settings` 卡片内，复制一个现有的 `.settings-row` 结构，
   改掉内部元素的 id（如 `settings-color-*`）
2. **CSS**：`source/css/settings.css` 里现有 `.settings-btn`、`.settings-status` 可直接复用，基本不用新写
3. **JS**：`source/js/site-settings.js` 里完整模仿 `pending.avatar` 那条链路：
   - `initPanel` 里给新元素绑事件（参考头像的 apply/reset 两段）
   - 新建一个 `applyXxx()`（读 localStorage → 改页面样式）和一个 `resetXxx()`
   - 在文件末尾 `DOMContentLoaded` 启动块里调用新的 `applyXxx()`
   - 新键名沿用 `snowtrace.xxx` 命名
- **原理**：理解「设置值 → localStorage → 启动时应用」三段式，以后任何「记住我的偏好」功能都是这个套路

### 5.10 加评论系统（★★★）

- **文件**：`_config.butterfly.yml` 第 537~661 行 `comments` 段落
- **原理**：静态站没有后端，评论要「借」第三方服务当数据库。主流选择：
  - **Giscus**：用 GitHub 仓库的 Discussions 存评论，免费、无服务器、和你已有的 GitHub 账号打通（推荐）
  - **Twikoo / Waline**：需要自己部署一个轻量后端（有免费方案）
- **做法**（以 Giscus 为例）：先在 giscus.app 按引导配置并生成一串参数 → 把主题配置里
  `comments.use` 填上系统名、`giscus` 段落填上参数 → 部署
- **注意**：评论区会出现在所有没写 `comments: false` 的页面；不想开放的文章记得在 front-matter 关掉

### 5.11 访客统计（★★）

- **文件**：`_config.butterfly.yml` 第 447~450 行 `busuanzi`
- **做法**：把 `site_uv` / `site_pv` 开关改 true，侧边栏「网站信息」卡片就会出现访问量
- **原理**：页面加载时引入「不蒜子」的统计脚本，由第三方记录访问数据
- **注意**：数据存在第三方、不可迁移；想要专业统计可研究 `umami`（同文件第 705~718 行的配置段），但需要先部署一个 umami 实例

### 5.12 搜索体验优化（★★）

- **文件**：`_config.butterfly.yml` 第 480~499 行 `search` 段
- **做法**：把 `local_search.preload` 改为 true
- **原理**：搜索数据存在 `search.xml` 里（由 `hexo-generator-searchdb` 生成，生成参数在 `_config.yml` 第 97~101 行）。默认是「用户第一次点搜索才下载」，preload 后随页面提前下载，首次搜索秒开；代价是首页多加载一个小文件

### 5.15 站点地图 + 搜索引擎收录（★★★）

## 七、安全实验的习惯

1. **一次只改一处**：改完立刻本地看效果，好了再改下一个。一次改十个地方，出错都不知道是谁的锅
2. **小步提交**：`git add . && git commit -m "做了什么"` 是免费的后悔药
3. **改坏了怎么办**：
   - 还没提交：`git checkout -- 文件路径`（放弃该文件所有改动）
   - 已提交：`git log --oneline` 找到坏提交之前的那一条，`git revert 提交号`
   - 整个乱套了：`git log --oneline` 找到某个好的版本，`git checkout 提交号 -- .` 再重新提交
4. **本地先跑通再 push**：`npm run generate` 报错的话，Actions 也会报错
5. **学会看日志**：本地构建报错会指出文件名和行号；线上失败看 Actions 页面里红色的步骤
6. **浏览器 F12 是你的显微镜**：Elements 面板看页面结构、Console 看 JS 报错、Network 看哪些文件加载慢/失败

## 九、案例解剖：网页发文功能是怎么实现的

「写文章」页（导航栏新增项）是理解「静态站如何借力 API」的最佳样本，数据流如下：

```text
浏览器（写文章页）
  ├─ 表单（标题/分类/标签/摘要/正文）   source/write/index.md 里的 HTML
  ├─ 逻辑                              source/js/post-editor.js
  └─ 样式                              source/css/post-editor.css
        ↓ 点「发布」：拼 front-matter + 正文 → base64 编码
        ↓ 调 GitHub API：PUT /repos/cooooh/cooooh.github.io/contents/source/_posts/xxx.md
        ↓ 凭据：你保存的 fine-grained 令牌（Authorization 请求头）
GitHub 仓库 main 分支多了新文件
        ↓ 推送触发
GitHub Actions（deploy.yml）构建部署
        ↓
snowtrace.top 上出现新文章（1~2 分钟）
```

**核心概念逐个对应**：

| 概念 | 在本功能里的位置 |
|------|----------------|
| 无后端怎么办 | 把 GitHub API 当「写接口」，仓库当「数据库」 |
| 身份认证 | fine-grained PAT：只授权一个仓库的 Contents 读写，存浏览器 localStorage |
| front-matter 生成 | `buildPostFile()` 函数把表单拼成文章文件的开头 |
| 中文编码 | `utf8ToBase64()`：`TextEncoder` + `btoa`（btoa 原生不支持中文） |
| 创建 vs 更新 | 先 GET 看文件是否存在，存在则带上返回的 `sha` 走更新 |
| 错误处理 | `friendlyError()` 把 401/403/409/422 翻译成人话 |
| 草稿 | 表单 `input` 事件防抖 400ms 后写入 localStorage |
| 预览 | marked（第三方解析库，`source/js/vendor/` 下）把 Markdown 转 HTML |

**值得读的三个细节**：

1. 为什么脚本开头有 `if (!document.getElementById('pe-title')) return`——防御性写法：保证脚本被任何页面加载都不会报错，只在写文章页干活
2. 为什么「查是否存在」要多一次请求——GitHub 的内容 API 规定更新必须带旧版本的 `sha`，这是防止覆盖别人的并发修改
3. 为什么令牌存 localStorage 而不是放进仓库——仓库是公开的，放进去等于把钥匙挂在门口；localStorage 只有你的浏览器里有

**安全边界**（想清楚再往外扩展）：

- 令牌过期（GitHub 强制 fine-grained 令牌设过期时间）→ 过期后在页面里重贴新令牌即可
- 令牌泄露（比如在别人电脑上登录过）→ 去 GitHub 撤销令牌即可，网站代码不用动
- 如果哪天想「多台设备都能发文」→ 令牌不能互相复制，每台设备保存一份自己的即可（或升级到 OAuth 方案，那是后话）

**练手建议**：给它加一个「发布前二次确认弹窗」，或加一个「系列」字段写进 front-matter——都在 `post-editor.js` 的 `buildPostFile()` 里改。
